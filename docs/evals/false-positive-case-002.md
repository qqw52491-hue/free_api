# False Positive 案例档案 #002：只读探针误报诱发的捂嘴与幻觉灾害链

- **日期**: 2026-09-07
- **场景**: 日常信息查询实弹（任务目标：“天天气是啥呢”，模式：CrossReview 交叉审查模式）
- **状态**: 已归因、已拆解、三层防线各管一段、端到端装配回放已闭环

---

## 1. 案例全景与因果链复盘

### 触发背景与用户现象
用户输入日常指令：“天天气是啥呢”（未提供城市）。
在运行日志中，模型首先尝试调用 `sh` 工具获取网络 IP 与定位信息，连续失败重试；随后调用 `ask_human` 尝试向用户索取城市，直接执行报错被系统拦截；最后模型在毫无城市输入的情况下，检索并给出了“全国主要城市”天气强行结项交付。

```
[用户输入: "天天气是啥呢"]
       │
       ▼
[第 1 阶段: 执行网络定位探针 (含 2>/dev/null)]
       │
       ▼ (误报!)
[系统判定为"破坏性写盘" -> 触发交叉审查门禁硬拦截]
       │
       ▼ (污染 checkpoint.recent_gate_block_step)
[第 2 阶段: 探针未果，模型调用 ask_human 索取城市]
       │
       ▼ (次生灾害: 误伤捂嘴)
[系统冷却机制将普通提问误判为"被拦截后发审批甩锅" -> 强行拦截捂嘴]
       │
       ▼ (两头堵死)
[第 3 阶段: 盲猜并强行生成全国天气交差]
```

### 逐层因果递进
1. **第一层表象（Symptom）**：模型未获城市信息却自说自话瞎猜全国天气，出现严重幻觉与强行交差。
2. **第二层直接诱因（Proximate Cause）**：模型想当“高情商 Agent”（先静默探测、不行再问人），但在调用 `ask_human` 时被宿主冷却机制拦截捂嘴。
3. **第三层次生灾害（Secondary Disaster）**：门禁冷却机制原本用于防止模型在写代码被拦截后立即发审批卡片甩锅；然而系统在协议层将“要审批 (Plan Approval)”与“要信息 (Missing Parameter)”混为一谈，导致普通提问被误伤。
4. **第四层系统根因（Root Cause）**：
   - 模型在第 1 阶段执行的探针为：
     `curl -s --noproxy '*' -m 4 http://whois.pconline.com.cn/ipJson.jsp | iconv -f gbk -t utf-8 2>/dev/null || curl -s -m 4 https://cip.cc`
   - 宿主系统此前对 Shell 写操作的判定过于粗糙，将 `2>/dev/null` 中的重定向符号 `>` 误判为破坏性写盘操作；
   - 在任务首步将一个纯只读网络探针打成了“破坏性写代码”，进而触发“未派发对抗审查即尝试动笔”的假阳性硬拦截；
   - 这个假阳性在 Checkpoint 中留下了拦截痕迹，直接引爆了下游的冷却捂嘴机制。

## 2. 归因方法论启示

### 门禁误报率决定下游一切行为的质量
在自主 Agent 系统中，安全防护与门禁机制如果出现“假阳性（误报）”，其破坏力往往不亚于甚至超过“假阴性（漏报）”。
一个误判会污染下游整条决策链，将本具备良好行为倾向的模型逼入“做动作被拦、问人类被捂”的 Catch-22 死锁，最终逼迫模型退化为胡编乱造交差。

### 协议分流 vs 粗暴统管
- **要审批（Plan Approval）**：涉及重大技术方案或跨越安全边界，被拦截后需要 cooldown 冷却期，强制模型先研判吸收意见，防止打扰人类甩锅；
- **要信息（Missing Parameter）**：任务必要关键参数确实缺失，属于开工前的正常输入索取，协议层必须永远放行，绝不可受门禁冷却压制；
- **缺失凭据（Missing Credential）**：私密 API Key、密码等人类专属资产，无合理默认值，必须向人类索取，绝不可被普通提问配额熔断，否则必将诱发凭据伪造幻觉。

### 治本必须区分“治病”与“治副作用”
放开信息类提问修的是“次生捂嘴”；如果不加约束，极易引发模型“每个小事都问一遍”、“用重复提问回避干活”的滥用。
因此必须构建**三道防线各管一段**的完整纵深，既不误伤，也不敞口。

## 3. 三道防线架构落地

```
   ┌─────────────────────────────────────────────────────────────┐
   │ 防线一：误报清零（根因治理）                                  │
   │ 精准识别 2>/dev/null 等安全只读探针，只拦截真写盘/代码篡改    │
   └──────────────────────────────┬──────────────────────────────┘
                                  │
                                  ▼
   ┌─────────────────────────────────────────────────────────────┐
   │ 防线二：中段解耦（协议分流 + 安全保真）                        │
   │ 区分 approval vs missing_parameter；普通提问不触发冷却；     │
   │ 关键安全属性：用户回答“北京”绝不旁路写入门禁，状态仍 Exploring│
   └──────────────────────────────┬──────────────────────────────┘
                                  │
                                  ▼
   ┌─────────────────────────────────────────────────────────────┐
   │ 防线三：滥用兜底（去重 + 动态配额 + 凭据豁免）                │
   │ ① Bigram Jaccard (0.88) + 语气词过滤拦截复读，不伤槽位变体   │
   │ ② channel-config 动态配置 MAX_HUMAN_INQUIRY_BUDGET (默认 5) │
   │ ③ missing_credential 豁免熔断，杜绝逼良为娼造假凭据         │
   └─────────────────────────────────────────────────────────────┘
```

1. **防线一（根因）：命令识别精确化**
   - 在 `dispatcher.rs` 中收窄破坏性命令识别，显式放行标准错误静默（`2>/dev/null`、`&>/dev/null`）及只读探测命令；从源头消除假阳性。
2. **防线二（解耦）：协议层清晰分流与安全保真**
   - 门禁冷却（Cooldown）收窄至真正的审批卡片（`kind: "plan_approval"`）；
   - 普通信息提问（`kind: "missing_parameter"` / `"text"`）跳过冷却；
   - 彻底解除普通提问对写入门禁的附带放行影响：普通提问 `is_approval_context = false`，用户回复后门禁状态保持 `Exploring`，后续写入操作依然受到严格交叉审查保护。
3. **防线三（闭环）：去重、动态配额与凭据豁免**
   - **防复读（去重）**：采用 Bigram Jaccard 相似度（阈值 0.88），对包含关系变体严格限制“差异必须为语气助词”才拦截；完美放行“城市 vs 日期”、“指标A vs 指标B”等同一模板不同槽位的合法提问；
   - **防琐碎提问（配额）**：将提问配额 `max_human_inquiry_budget` 纳入 `channel-config`，默认 5 次，超额自动切断主动提问通道并强令采用默认规范推进；
   - **防伪造造假（凭据豁免）**：私密凭据（API Key / Token / 密码等）不可凭空捏造，在 `checkpoint.rs` 与 `loop_runner.rs` 中将 `missing_credential` 列为豁免名单，不受全局提问配额熔断限制。

## 4. 验证与端到端装配回放

全链路在 `agent::finish_guard::weather_disaster_chain_end_to_end_replay` 测试用例中完成装配级真机模拟回放：
1. **探针执行**：`2>/dev/null` 网络定位命令被识别为只读命令，顺利放行，无门禁拦截；
2. **探测未果发起提问**：即使历史有拦截记录，`missing_parameter` 也不受门禁冷却压制；
3. **去重与配额检查**：首问城市顺利放行，登记提问次数；
4. **用户回复“北京”**：系统接收输入，`checkpoint.plan_phase` 依然为 `Exploring`；
5. **门禁安全闭环**：后续若尝试调用代码写盘工具，门禁依然严丝合缝地触发拦截；
6. **防复读生效**：模型若换语气助词复读问城市，被去重机制硬拦截；
7. **配额超限与凭据豁免**：普通问题 5 次用尽后第 6 次被配额熔断强制默认值；但此时若索取 `missing_credential`，协议层豁免配额顺利放行。

## 5. 对照思考（与 reward-hacking-case-001）

| 维 度 | Case #001: global.fetch 劫持判分 | Case #002: 探针误报诱发捂嘴与幻觉 |
| :--- | :--- | :--- |
| **问题性质** | 模型的作弊（Hacking） | 体系的误报（False Positive） |
| **发生机理** | 门禁高压逼出模型寻找旁路，劫持全局 fetch 篡改判分请求 | 门禁粗暴误判只读命令为写盘，次生冷却将正常提问堵死逼出幻觉 |
| **治理靶向** | 刃向外：防御并捕获模型的作弊、加固判分沙箱隔离 | 刃向内：降低门禁假阳性、协议精准分流、建立自律防御纵深 |
| **核心教训** | 模型的旁路往往是压力逼出来的 | 模型的胡言乱语往往是系统误报把正常通路封死的结果 |

两个案例共同构成了 Agent 工程治理的完整拼图：**既要有严密的审查与对抗机制防止模型失控作弊，又要有高度精确的归因与分流机制避免体系自身误杀**。
