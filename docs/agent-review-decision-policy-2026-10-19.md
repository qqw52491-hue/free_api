# 审查判决与疑问边界（2026-10-19）

## 实测触发

会话 `d486283e` 的 run `ff2528ac` 比较网络传输与 U 盘速度。首次方案审查返回 `approved`、0 条 blocking、正确性 58 / 安全性 92 / 规范 78（平均 76）。后续命令被「正确性 < 60」评分门拦截，同时 F1～F3 三条 question 自动成为 pending 待办，导致 11 次交付先被本地待办门挡回，并非终审模型执行了 11 轮。

复审撤回旧疑问后，又产生 F4～F6 三条 question。部分意见有价值，例如不能把网络吞吐上界等同于真实文件拷贝速度；但“还有疑问”不应自动升级成“还有未满足的验收义务”。

## 本次边界

- 方案与子审查不再以评分高低、评分缺失决定放行，也不再给 approved 合成高分卡。历史评分字段及聚合保持可读，仅作参考。
- 方案门仍等待实际审查结果与批次齐套；仅有 consumed 标志或旧评分，不冒充有效审查。具体 blocking、明确 rebuttal、升级会审、人工审批和结构化方案要求继续生效。
- 同一道审查的生效修订裁决复用台账 task_id/attempt_id，以已交付的最新 attempt 为准；其他审查员的独立裁决不被覆盖。原判决仍在历史记录中。
- 新 question/suggestion 保留在回执与审查记录中，不自动进入强制 TODO。question 是否需要进一步取证由审查员结合用户目标判断：若缺证据影响明确验收要求或存在具体阻塞风险，应说明影响并明确列为 blocking。宿主不按“读够没”等语义猜测升级。
- 旧 checkpoint 中宿主固定格式的 question/suggestion 待办，在上下文中标为历史参考，不要求销账，不伪造 done。普通用户 TODO 和阻塞审查待办仍保留原规则；正文里出现 QUESTION 不构成豁免。
- 全局/报告问题没有源码行号也可构成 blocking，不再仅因 location 为空强制降级。严重度的真实性仍由审查员判断。
- 子审查新派发取消强制评分提示，旧子审查续跑更新宿主规则副本，原始证据与模型判决保留。界面不再用评分卡宣称“门禁合格放行”。

未修改 Git 基线、扫描边界、命令安全分类、冻结验证、状态机、模型重试或输出预算。终审已有的 score 字段仍作为遥测接口保留，不参与通过判定；本次不重写该接口。

## 回归与限制

本地假模型覆盖真实异步派发与落库：无评分、无缺陷结果只需一次请求，无评分补答。合成事故回执经实际解析、reducer、checkpoint 保存恢复、写入门和交付待办检查，覆盖低分/无分批准、question 保留展示、全局 blocking 仍拦截。另覆盖旧格式参考、用户任务保护、明确打回、复审覆盖本题旧裁决及保留其他审查员意见。

完整 Rust 回归：`cargo test --lib -- --skip clipboard`，1161 通过、0 失败、10 项原有忽略、1 项剪贴板过滤。前端类型检查 `npx vue-tsc --noEmit`、Rust 编译检查 `cargo check` 与前端构建 `npm run build` 均通过。

未调用付费模型，未修改或重放用户正在运行的任务。本地回归只证明机制边界，不证明 reviewer 一定定级正确或真实任务必然提速。历史剩余空间与设备总容量混淆仍属于需正确使用证据的语义问题。应用需要重新构建并重启 Rust 后端后生效。
