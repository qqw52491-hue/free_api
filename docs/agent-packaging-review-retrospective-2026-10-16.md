## 1. 结论与用户反馈

用户反馈：**反复检测仍然偏重，最终审查的粒度不好控制。** 后续优化要保留这条问题，不能又通过增加必填证据、固定检查次数或更多强制扫描来处理。

这轮 Agent 有实际执行能力：服务器上 GPU/nogpu 两版安装包已生成，nogpu 包传入 U 盘并取得两端 SHA-256 一致的证据。但是，输出回收不完整、重复计算与过重的收尾核验造成明显折返。

必须区分：**本轮大量重复发生在执行 Agent 自检阶段，尚无证据表明是最终审查要求它重复。** 打包执行 run 没有 `finish` / `prepare_finish` 步骤，也没有子审查派发。前一轮有两次方案审查，但不等于后续每次复算都是审查员要求。

本次不能据此宣称“最终审查已经合理”，也不能把全部耗时归给终审或模型能力。要分别检查执行反馈、自检策略、方案审查和交付审查。

## 4. 重复核验的已确认触发点

### 4.1 SSH 辅助脚本停止读取输出，但仍等待进程结束

当时文件：会话临时目录中的 `ssh77.py`，关键逻辑位于约 36–63 行。省略认证等内容后的结构如下：

```python
deadline = time.time() + 90
while time.time() < deadline:
    # 轮询并读取 SSH PTY 输出
    ...

try:
    os.waitpid(pid, 0)
except Exception:
    pass

# 没有继续排空剩余输出，也没有把子进程退出状态作为脚本退出码返回
```

确认的代码事实：

- 输出读取循环有 90 秒期限。
- 离开循环后，仍可能阻塞等待 SSH 子进程结束，但不再持续读取后续输出。
- 等待得到的退出状态未传播；本地脚本正常退出不能证明远端命令成功。

对应运行现象：打包执行 run 的 seq 18 已看到远端正在实际解包；seq 20 看到解出的目录；seq 21 取得的本地日志却只有 8 行，停在 GPU 载荷哈希阶段的标题。随后 seq 22、26、27 又安排复算，seq 28 才取得较完整的结果文件。

判断：**执行反馈不完整是本轮重复核验的重要触发因素。** 不能据此断定每一次重复都由这一处引起；也尚未独立证明本轮发生了 PTY 缓冲区堵塞，尽管停止读取会带来该风险。

这个辅助脚本是任务中临时生成的，不能直接把它的缺陷说成 Rust 原生 shell 工具本身只读 90 秒。后续修复应先定位辅助脚本及其使用方式。

### 4.2 本地、远端执行位置混淆

执行 run 的 seq 9 在本地后台任务中使用服务器路径 `/home/pack/verify.sh`，seq 10 回收结果明确报告路径不存在。后续才改为将脚本送到远端执行。

seq 28 又同时出现本地缺少服务器路径、远端缺少本地 U 盘挂载点的回执。seq 29 才进一步分开环境核对。

这是明确的脚本组织 / 执行位置问题，不能通过要求更多包完整性检查解决。

停止 GPU 传输后的 run，seq 9 又启动了授权排除与完整性检查。脚本安排了多次 `tar -tzf`、`gzip -t`、条目计数和路径筛选。对 gzip 包做目录遍历也可能需要流式读取、解压全包，不能因为命令是“只读 / 列目录”就当作低成本。

这些是脚本安排的操作，**不表示取消前已全部执行完**。在观察点，日志仍停在 GPU 包授权条目检查的开头。

### 4.4 停止传输命令过宽，并出现重复失败

停止 run 使用 `pkill -f 'rsync'`，同一指令出现失败重试，回执为退出码 `-1`。其外层 `sh -c` 命令行自身也包含 `rsync`，存在匹配并终止自身的风险。随后 Agent 改为先查询进程，并在描述中写出“避免自杀”。

命令结构和后续自述符合自匹配解释，但未做隔离实验，不能仅凭 `-1` 认定唯一原因。广泛匹配还可能影响其他 rsync 任务；本轮没有证据证明其他传输被误杀。

核对记录表明传输进程后来已停止；停止后的 GPU 文件仍是残片，需要如实标明状态。

### 4.5 其他观察，暂不合并归因

- 前一轮方案中，空间不足与直接覆盖旧大包的风险有实际依据；同时，部分自报只读的 shell 探测被写入门拦截。需要另查动作分类，不能一概判为必要保护或误拦。
- 前一轮 `ask_human` 等待和执行轮 `wait_jobs` 都出现过 480 秒派发看门狗超时。记录能证明超时，不能仅凭错误文案断言内部死锁。
- 同一后台日志连续读取且无变化触发过复读拦截。它没有解决输出缺失问题；不应据此直接增加新的反复读取检测器。

## 5. 审查与验证粒度：后续优化方向

下面是待验证的设计方向，不是已经实施的新规则，也不是让模型新增一张必填表。

### 5.1 先修事实反馈，再评价模型是否不会收敛

优先让长命令在执行期间持续排空输出，保存可回查的结果；中断、超时、截断和仍在运行要明确区分。退出码应反映实际子进程状态，不能把“辅助脚本结束”包装成“远端检查通过”。

需要限制输出时，明确可见范围和已保存原文的位置；不是无限制地把整份大日志塞进上下文。

### 5.2 复用已存在、确实针对同一产物的证据

优先复用已有 output_id、结果文件和后台任务回执。产物未变化时，不应因为进入下一阶段就默认重跑同一条全量检查。

宿主可以核对产物身份、指纹和保存记录；“这些检查是否足够支持结论”仍由模型 / 审查员判断。不能用固定证据条数、关键词或“做过一次检查”代替充分性判断。

### 5.3 把具体疑点和昂贵全量检查对应起来

例如：

- 判断传输是否完成：看传输退出状态、目标文件状态及适用的一致性证据。
- 判断包是否排除授权文件：复用本次构建的实际包清单或解包核对结果；不能只读打包脚本就宣称实际包合格。
- 判断自解压包是否能安装运行：目录 / 哈希检查不等价于安装测试；未执行就披露未验证。

是否需要重新做完整解包或安装测试，应根据用户目标、已有证据和具体疑点决定。不按固定文件大小阈值自动免检，也不把任何检查任务都升级为全量重装。

### 5.4 执行自检、方案审查、终审分别评估成本

终审宜针对交付断言与已有证据的缺口，复用有效记录。若指出实质缺陷，仍应处理；但不应把每个历史风险、调查线索都重新变成验收义务。

执行者自己也可能过度检查。因此，不能只修改终审提示词，就宣布本轮重复问题已解决。

用户要求暂停某项传输时，先确认停止和残留文件状态；尚未完成的原任务要求如实保留、披露。不要为了收尾又默默启动多轮大包扫描，也不能把暂停当成此前全部验收要求已通过。
