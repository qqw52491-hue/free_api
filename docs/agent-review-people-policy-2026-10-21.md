# 审查人数选择与实际派发对齐

## 需求与查证

用户报告已选择多人，但运行 `d1a55fde-6ae5-403b-9d87-2f1e6d43b4b0`
只有单个终审上下文，没有子 Agent 派发。该轮是 `auto`、`stage_review_mode=none`。
当时未保存完整路由入参，因此不能据此断言开关传丢；代码确认旧
`stage_review_committee` 只被阶段审查读取，方案审查和终审不受它影响。

用户明确选择的修复范围是：**方案审查和终审都遵循人数选择，阶段审查仍按原条件触发。**
这次没有增加“复杂度自动打分后升级多人”的规则。

## 行为

- 默认自适应单审：一次审查一位，不因为专家库有多张卡就全部派发。
- 明确选择多人：正式提交方案及终审最多三位，各角色独立判断。同一模型可承担多个角色，
  不保证三个不同模型，也不自动从未授权模型池补人。
- 正式 `submit_plan` 在 Auto 下仍执行安全策略；保留 Block/Escalate，明确多人选择不再被
  FastPass 免审覆盖。仅生成一段分析建议不强制补建方案审批，作为交付物进入终审。
- 人数选择不改变实际执行模式，阶段触发条件仍保持原样。正式派出的方案批次须收齐结果，
  复用原 CrossReview 判定逻辑核对实际 blocking/修订裁决；Auto 不能在该批未收口时又走免审写入。
- 方案批次继续使用原 batch_id、task_id、checkpoint 和备用模型路径，一批只记一轮预算。
  派发快照按物理审查任务保存，人数以实际启动成员计。没有可启动成员不批准方案；
  可用角色、模型配置、输入契约或容量不足时披露实际数量和原因，不把人数不足合成质量缺陷。
- 多人方案审同一个提交版本，由主 Agent 汇总修订；多人不并发覆盖 `revised_*`。
  `plan_review_can_finalize` 是宿主控制的内部元数据，模型不能自行授权；单审保留原定稿能力，
  对质继承该权限。没有新增模型必填项。
  独立成员的升级裁决也按各自最新审查保留，不能被其他成员稍后返回的批准冲掉。
- 多人终审并发调用既有审查流程，保留各成员的具体阻塞、实际宿主复验失败、停止和通道失败。
  汇总不靠分数投票抵消缺陷；各成员独立归档，避免并发改写同一个日志文件。
  同批宿主复验串行执行，模型与只读取证仍可并发；保留既有验证语义和预算。
- 多人选择覆盖仅机械/只读问答的默认免 LLM 终审；空交付物仍沿用原空材料处理。
  方案或终审只有一位可用时明确披露为实际单审，不宣称完成多人会审。
- 多人模式及审查相关角色/模型配置绑定就绪收据身份，避免开关改变后直接复用旧单审收据。
  新增可选收据字段默认空，兼容旧检查点；不改数据库表，不改变原冻结验证命令的复用身份。

## 界面

保留 `stage_review_committee` 字段名兼容既有配置，界面改为“自适应单审（1 位）／多人审查（最多 3 位）”。
明确说明作用于正式方案、终审和已经触发的阶段审查；候选数与实际人数分开。
关闭阶段审查不再禁用全局人数选择。删除默认跨模型家族、选中即必定触发阶段审查等不成立的承诺。
