# Free API：审查、验证证据与多 Agent 收敛——讨论纪要

> 日期：2026-10-17
> 目的：保存本轮对话形成的架构认识、已经落地的改动、仍未解决的问题和下一次会话的切入点。
> 性质：**讨论纪要与下一轮工作参考，不是新增的宿主硬门禁或产品规格**。结论需以当前代码及后续实测复核。

## 1. 当前的整体判断

Free API 已有相对完整的复杂 Agent 运行骨架：主 Agent 编排、入口 triage、方案审查与修订、按需子 Agent、角色卡结构化输入/输出、阶段审查、最终 Reviewer、工具输出与证据回查、checkpoint 恢复和交付收尾。

使用者报告：**已经运行过数百步骤的真实任务**，中途的执行与审查总体能推进，Reviewer 也会发现问题；比较突出的反复卡点在**最终交付**。这是有价值的现场反馈，但不是统计意义上的完成率或缺陷检出率，不能由此断言全部复杂任务稳定完成。

现阶段更有价值的方向是**让现有机制协作并收敛**，而不是继续堆叠流程、常驻角色或新的状态机：

- 主 Agent 自主组织任务，按需调用 worker / writer / reviewer 等角色。
- 工具和宿主提供真实执行事实、访问边界与必要的确定性不变量。
- Reviewer 负责有上下文的质量判断、质疑旧证据的适用性和提出具体修复要求。
- Finalization 负责核对必要条件与可靠地提交终态，而不是复制一套语义质量审查。

## 2. 关键概念：验证只是审查的一项证据

建议始终区分三层：

| 层次 | 回答的问题 | 谁负责 | 注意 |
| --- | --- | --- | --- |
| **验证执行事实** | 某个命令在什么时间、环境和对象上执行？退出码与原始输出是什么？ | 宿主与真实工具回执 | 当时 PASS 不自动证明新版本 PASS |
| **证据对当前交付的适用性** | 旧验证覆盖当前产物、输入、依赖及断言吗？ | Agent/Reviewer 结合材料判断，宿主核验来源与硬约束 | 文件指纹一致也不证明外部环境完全不变 |
| **最终质量审查结论** | 当前成果是否满足用户目标、质量要求与冻结验收义务？ | Reviewer + 不可绕过的宿主事实门 | Reviewer 不能凭自述制造真实的验证通过 |

因此：**重新审查 ≠ 重新验证**。补充交付说明、新增可查询证据通常应重新审查其充分性，而非无理由重跑昂贵的历史命令；真正修改产物或契约则要重新判断旧证据是否仍适用。

40GB 安装包例子：第一次校验完整性、内容正确性，但启动检查失败。Agent 修复启动问题后，须针对启动缺陷补验；如果重新打包改变了安装包，也要重新考虑完整性证据。若只是解释文字写得不清楚，无须默认对 40GB 再执行一次全量扫描。

## 3. Reviewer 打回的对象是问题，不是把所有成果清零

已有 Blocking/Nit 等分类**应保留**，不要另建一套互相冲突的阻塞状态体系。

- **Blocking**：当前确实阻碍交付的问题，需指明具体事实、位置、影响和可验证的修复条件。
- **Nit**：非阻塞建议，不能因风格偏好强制任务重来。
- **阶段审查阻塞**：仍按已有 checkpoint / 阶段流程维护，不因复用旧验证回执而解除。
- **宿主硬性阻塞**：例如实际越界、必需验证失败、后台作业未完成，仍由宿主按事实检查；Reviewer 不能单纯宣布通过。

增量审查的长期目标：

```text
首次审查：A 通过，B 通过，C Blocking，D Nit
                  ↓
Agent 针对 C 修复并补证
                  ↓
Reviewer 核对 C 是否闭合，并审视这次修改是否影响 A/B 或引入新问题
                  ↓
保留仍适用的旧结论；只对有疑点的部分补验；最终仍评价当前完整交付
```

核心提醒：**增量审查不是增量放行**。本轮可重点检查变化和未闭合问题，但最终对当前全部交付负责。

“哪些结论受影响”很难机械判定。底层依赖、环境和间接调用链可能改变证据适用范围。不要写一个简单的 `affected=false` 就永久锁死结果。Reviewer 可提出疑点及补验要求；宿主适合核实来源、契约和范围等可确定事项，不应假扮全知的影响分析器。

## 4. 本轮已经落地的实现（以提交为准）

### 4.1 证据登记与终审取证

提交：`c5e11aa feat(agent): persist verification evidence and expose it to final review`

- `src-tauri/src/agent/evidence_store.rs` 提供 `evidence_record`、`evidence_find`、`evidence_inspect`、`evidence_compare`。
- 可记录执行输出来源 `output_id`、相关产物快照以及 Agent 对目的和结果的声明。
- 大文件使用有界分段采样；**样本摘要不等于全文件完整性证明**。检索结果也不自动成为 PASS。
- `reviewer_gatekeeper/evidence.rs` 与最终审查接通了已有证据读取能力。

### 4.2 冻结验证与 Reviewer 判决的有限解耦

提交：`c719e97 fix(agent): reuse frozen verification across final review retries`

- `FrozenVerificationRun` 保留由宿主真正执行、且成功的冻结义务结果；这份执行事实与 Reviewer 的通过/打回判决分开判断新鲜度。
- 同一运行、工作区、交付材料、范围、验收契约及副作用条件匹配，且旧回执有效时，可不自动重跑旧冻结命令，仍需 Reviewer 核对适用性。
- Reviewer 只打回说明或补证时，旧验证可继续作为证据。中途阶段 Blocking 拦截不应擦除此前有效的执行记录。
- 产物/契约变化、旧结果失败或缺少可信旧回执时，走原验证路径。Reviewer 主动补验的真实失败不得被旧 PASS 覆盖。
- 没有改变既有 Blocking/Nit 类型，也没有搭建一整套新的冻结验证状态机。
- 针对性测试以真实冻结命令执行计数检查：第一次执行 1 次；仅补说明/证据或阶段拦截不新增执行；修改产物或契约后再执行。验证失败不得复用。
- 当时完整 Rust 回归：**1155 passed、0 failed、10 ignored；另过滤 1 项剪贴板测试**。这不是实际模型端到端效果的证明。

**准确的边界**：当前重点解耦的是**冻结义务命令**；自适应验证、可配置额外验证、逐条审查结论的增量复用尚未全部实现。独立“执行事实”目前通过交付收据中的可选回执字段保留，不等于已经建成一个覆盖任意环境变化的永久可信缓存。

## 5. 方案讨论、执行中推翻与多 Agent 收敛

系统的三个纠错时点：

1. **事前**：方案讨论、反驳与交叉审查，尝试发现错误假设、缺失需求和风险。
2. **事中**：执行时获得新证据，可以通过 `request_retriage` 或携带 `revision_reason` 的方案修订推翻局部先验。
3. **事后**：阶段 Reviewer / 最终 Reviewer 针对具体缺陷打回，Agent 修正并带证据再次提交。

这三种能力有机会提高复杂任务质量，但也会制造重复讨论、反复推翻和交付死循环。关键不是 Agent 数量、辩论轮数或打回次数，而是**每轮是否减少了不确定性、解决了具体问题并保留仍有效的成果**。

Reviewer 不是天然正确。若主 Agent 已有真实测试证据，Reviewer 不能只凭“另一种架构看起来更好”就给 Blocking。多 Agent 使用近似模型、相同盲区时，也可能一起看漏问题；实际取证比增加辩论人数更重要。

结构化角色卡、输入/输出契约以及通信机制能提高协作的可消费性，但**结构化 ≠ 语义正确**。长期应观察这些产物是否真正被执行者使用、反馈是否可闭合，而不是仅检查 JSON 格式是否完整。

## 6. 下一阶段优化顺序（讨论建议，不是承诺）

**优先级 A：先用真实失败案例追查交付摩擦**

- 统计同一 run 的 `prepare_finish` / `finish` 调用次数、重复执行的昂贵命令与被打回原因。
- 区分 Reviewer 真实发现问题、宿主必要硬阻塞、重复验证、误导性证据和文案问题。
- 修复能被复现的耦合，不因为“可能发生”就新增一层门禁。

**优先级 B：提高现有 Reviewer 意见的有效性**

好的 Blocking 应能说明“**哪里错、证据是什么、为何影响目标、要满足什么修复条件**”。观察修复后同一问题是否仍存在、是否误把偏好当缺陷、是否产生新的连带问题。

**优先级 C：在证据充分时开展更细的增量审查**

先看已有 Reviewer/Checkpoint 是否能表达受影响项目和未闭合问题；必要时再新增最小数据字段。不要先把所有验收义务建成大而全的独立状态机。

**优先级 D：多 Agent 效益与收敛对照**

对相同模型与可比任务，比较有无前置方案讨论、阶段审查、结构化角色的成功率、缺陷漏检、平均修复轮数、Token 与时间。避免把单场成功归因于某个机制。

建议关注的指标：

| 维度 | 可观测指标 |
| --- | --- |
| 修复效果 | Reviewer 首次打回后，下一次提交解决原 Blocking 的比例 |
| 质量 | 独立判据或人工复查检出的真实缺陷、漏报与误报 |
| 收敛 | 同一问题被反复打回次数；方案 A/B 来回推翻次数 |
| 交付效率 | 重复冻结验证次数、重复扫描耗时、`finish` 阻塞类别分布 |
| 成本 | 总步数、Token、实际耗时、人工干预次数 |
| 恢复 | 中断/重启后是否保留目标、证据、修复进展且不误覆盖用户工作 |

## 7. 特别提醒：不要从这个纪要制造新门禁

- 本文件不是要求 Agent 每轮都填写“影响矩阵”“收敛分数”或新结构化表格的指令。
- 保留原来的权限、契约、阶段审查和 Blocking/Nit 职责，不默认推翻现有流程。
- 不把文件哈希当作所有环境变化的充分证明，不允许 Reviewer 自证冻结命令通过。
- 不因测试全绿就宣称“复杂任务已经稳定自动完成”；验证架构行为与验证真实任务效果不同。
- 当前目标是 **提升有效质量反馈 + 降低不必要的交付摩擦**；投入新理论或机制之前，先找对应的真实失败形状。
