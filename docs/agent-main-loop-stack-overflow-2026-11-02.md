# 主循环首次提问崩溃修复（2026-11-02）

## 现场与归因

本机两次首次执行都在完成入口分流、进入第一步后退出：

- `e5c78e68`：用户输入“早上好啊”，分流为 direct；重启后原运行被标记为中断。
- `9a6cf89d`：用户输入“继续把”，沿用会话检查点；退出时尚无已完成步骤。

系统 core 记录两次均为 `SIGSEGV`，不是任务停滞看门狗主动结束。两次栈顶一致：
`sqlite3RunParser → agent_mailbox::pending_page → deliver_main → turn_main → execution::run`。
第二次 core 中线程 TLS 位于 `0x7f6478dfa6c0`，崩溃时 RSP 为
`0x7f6478bfab90`；默认约 2 MiB 的工作线程栈已耗尽。GDB 回溯显示公共循环、
主循环、两层入口及 Tauri IPC 的 poll 帧累计占用约 2 MiB。简单的信箱表存在性
查询触发最后一次栈写入，不能据此认定数据库或查询本身损坏。

重构将大型主循环状态按值交给公共异步循环；未优化的调试构建在多层 future 构造、
移动及 poll 中产生大的栈帧。此前功能回归没有覆盖桌面入口这条完整调用栈。

## 修改

- 主循环状态在每轮交接时使用 `Box<MainExecution>`，保留独占所有权。
- 公共循环对每轮 future 使用 `Box::pin`，不再将完整 turn future 内联进驱动器。
- 桌面入口和工作区入口在等待下一层主循环时建立堆分配边界。

不增加线程栈配置，不改信箱业务规则、模型路由、任务判定或历史记录。

## 验证与边界

新增两个回归：

1. 检查真实桌面入口和公共驱动器的 future 类型大小，不启动 UI 或模型。
   本机调试构建中桌面入口由 95,872 字节降至 1,000 字节，驱动器由
   64,744 字节降至 24 字节；这是对象大小，不能直接当作整个调用栈大小。
2. 在显式 2 MiB 的 Tokio 工作线程上，经公共驱动器连续执行三轮真实信箱投递，
   核对消息仅接收一次、检查点内容与版本保留。使用临时数据库，无网络模型调用。
