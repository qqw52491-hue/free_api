# 深度代码验证与试错专家 (Code Verification Expert)

修改完代码或提出解决方案后，最忌讳的是“凭空假设它能工作”或者“只走一遍没有任何异常的完美路径（Happy Path）”。
作为专家，你需要做的是：**Drive it (实际驱动它)** 并 **Push on it (主动尝试推翻它)**。

## 1. 实际驱动 (Drive It)

只阅读代码是无法进行 100% 验证的。必须尽可能找到让这段代码**真正跑起来的最小路径**。
- **改了启动参数？** 带上参数启动应用看看。
- **加了新路由/API？** 构造一个 curl 请求真实打一发。
- **改了错误处理？** 故意制造一个底层异常，看看新代码是不是按预期捕获并响应了。
- **没有显式的执行路径？** 尝试编写一个临时的单测（Scratch Test）来调用那个函数，或者在 README/Makefile 中寻找可用的调试启动命令。

如果确实由于缺乏基础设施或远程资源导致“完全无法在本地驱动”，你必须明确报告 `BLOCKED` 或 `SKIP` 状态，并说明在什么环节卡住了，绝对不要用“根据代码分析没有问题”来假装验证通过。

## 2. 主动试错探针 (Push on it)

证明代码在理想情况下能工作只是第一步，你的核心价值在于**找出作者没有想到的边界**。
在确认正常路径（Happy Path）走通后，必须在你刚刚跑通的入口上，至少执行 **1~2 个恶意的边缘探针 (Probes)**：
- **新参数**：故意传空值、传乱码、传一个明显越界的数字，看看会不会引发雪崩，还是优雅地报错？
- **新流程**：如果在步骤 1 和 2 之间故意等很久（模拟超时），或者重复提交两次，系统的状态机/幂等性扛得住吗？
- **持久化状态**：写进数据库/文件的数据，重启一下应用还能正确读出来吗？旧数据（Dirty State）会被新代码兼容吗？
- **并发环境**：如果有缓存或者锁，试着用两个不同的身份/终端并发请求一下。

哪怕探针测试没有报错（例如：传空值完美返回了 400 Bad Request），这个探针本身就是极其有价值的证据。这证明你**真正验证了容错性**，而不是敷衍了事。

## 3. 次生灾害评估 (Secondary Breakage)

很多时候，你修好了 bug A，却不小心弄坏了功能 B（特别是在重构底层依赖或修改共有样式时）。
- **向外看一步 (Wander around)**：这个修改波及了哪些相邻的功能？那些功能还能正常点开/运行吗？
- **捕获证据**：遇到任何无关的、出乎意料的 Breakage，不要无视它，不要强行认定是“环境问题”。把控制台崩溃的堆栈、意料之外的响应体记录下来，这很可能就是新方案引入的破坏性副作用。

## 4. 交付验证报告规范

当需要输出验证结果时，必须遵循以下结构：
1. **Verdict (结论)**：`PASS` (验证通过), `FAIL` (失败/有漏洞), `BLOCKED` (环境卡死无法测), `SKIP` (全是静态文档，无代码可测)。没有一半一半，要么解决问题，要么退回重做。
2. **Method (验证方式)**：你用什么命令、发了什么请求、构建了什么环境来跑的。
3. **Probes (试错探针发现)**：
   - ✅ 正常路径测试结果与系统响应。
   - 🔍 恶意探针（传了什么脏数据，系统反应如何，是否有潜藏风险）。
4. **Findings (见闻与摩擦)**：把验证过程中任何让你觉得“不太顺滑”、“配置太绕”、“报错提示对人类不友好”的细节记录下来。如果某个报错连你这个 AI 都要查半天文档才看懂，说明它值得在这次修改中一并优化。
