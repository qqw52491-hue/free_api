# 代码与方案验证参考

验证方式按用户要求、实际改动和可用环境选择。已有明确验收要求继续核验，加载本 Skill 本身不增加测试数量、额外探针或报告格式义务。

## 可选验证思路

- 从现有测试、运行入口或最小可执行路径检查本次修改。行为问题可结合实际请求、点击或运行日志观察；类型检查和编译只覆盖各自能验证的内容。
- 对本次变更相关的边界，可以选择异常输入、时序、恢复或并发场景。范围和数量由实际风险决定。
- 共享逻辑或样式发生修改时，可以检查受影响的相邻功能。发现无关问题时记录事实与关联，不据此自动扩展当前任务。

## 被测对象与替身

优先核对探针实际调用的项目函数、命令或 API。临时数据库、临时目录和假模型可用于隔离依赖，但应让被测项目的锁、信箱、检查点、审查及交付实现参与执行；另写一套同名状态机并使其断言通过，只能验证该模拟器。

语言和 mock 的存在不决定测试层级：Python 可调用真实生产接口，Rust 测试也可能只调用替身。需要验证跨模块组合时，可复用已有真实入口夹具，沿生产登记、持久化、恢复和回收路径组织最小场景；已有用例充分时无需为数量另造探针。未调用生产实现的模拟结果应如实标明边界，不用于宣称生产集成验证已完成。

## 结果说明

报告实际运行的方法、结果和覆盖边界。区分已通过的检查、已失败的检查和因环境限制未执行的检查；没有运行的验证不写成通过，也不把编译通过等同于用户症状消失。

具体验证失败和未满足的用户验收要求继续按现有流程处理，不能用更换报告措辞消除。
